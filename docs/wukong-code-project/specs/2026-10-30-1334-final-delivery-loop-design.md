# 最终交付闭环设计

Status: Confirmed
Date: 2026-10-30（Asia/Shanghai）
Source: grilling
Spec approval: Pending user review

`Confirmed` 指用户已确认本轮完整需求共识；本技术文件尚待单独审阅批准，不能据此开始实现。基线：`main 4489cdd`、插件v0.17.1。关联：[体验优化 #93](https://github.com/wukongnotnull/wukong-animation/issues/93)、[既有PRD](../prd.md) FR-6/FR-7、[第二次实拍复盘](../reports/2026-10-30-production-delivery-review.md)。本设计细化最终交付，不扩大其他制作环节。

## 1. 问题与目标

当前 `delivery.mjs` 将 `user-modified` 合并为 `stale`，第15道签批没有绑定外部草稿目录的当前磁盘内容；旧清单有2044项文件，当前成片、字幕和草稿淹没在历史检查材料中。`operations.mjs` 的恢复状态采用全局来源签名，不能直接证明某个交付物的具体依赖是否变化。

用户已逐项确认：先完成最终交付闭环；简明清单只展示承诺产物，技术材料进入附录；验收绑定具体版本；缺项时仍展示可用成果，整单标明部分完成；历史验收按证据沿用；过期仅影响相关产物，无法判断时说明待核实。

目标：用户能回答“最新文件是哪份、哪些已验收、整单是否完成、缺什么、由谁处理”。本次不增加审片节点，不以文件生成成功代替验收，不改既有渲染与缓存复用算法。

## 2. 架构与组件边界

- `core/delivery.mjs` 保留中间工序的现有入口；增加最终交付汇总与精简Markdown。最终判定不再直接采用 `recoveryStatus` 的全局过期结论。
- 新增 `core/final-delivery.mjs`：最终交付契约、产物取证、逐项依赖、验收绑定和状态聚合。只读计算与显式保存分开导出，避免查询时隐式修改项目。
- 新增 `schemas/final-delivery.schema.json`，校验工程内 `.wka/final-delivery.json` 的version 1证据账本。既有 `.wka/decisions.json` version 1仍记录明确选择，不向其塞入未声明字段。
- `job.mjs` / `wka.mjs` 只在已有最终导出、独立字幕登记、既有签批边界增加证据记录；不通过重新执行 `final`、混音或签批来检查交付。
- `state.mjs` 的步骤、历史和既有批准身份保持兼容；交付证据引用批准ID，不重写旧history。最终状态与“流程已走到第15道”分别表达。
- director在最终交付中使用新汇总入口，给出明确产物、状态和下一步。中间审片卡片及交付清单行为不在本批统一改造。

新增CLI为 `wka delivery <片目录> --final --host codex|claude|generic [--aspect all|9:16] [--json]`。`--final` 缺省覆盖全部已确认画幅；显式单画幅只表示该画幅，不能冒充整片交付通过。原命令不带 `--final` 的行为、JSON v1与中间工序调用保持兼容。

## 3. 接口、数据与行为

### 3.1 最终交付契约

契约以最新明确确认的制作决定和变更为准，记录原始来源、确认时间及规范化投影。导演依据明确用户回复维护decisions，不自动解析自然语言为批准。

契约按画幅、格式、字幕形态和交付类型生成稳定产物槽位，例如 `16:9/video/mp4/burned`、`16:9/subtitle/zh`、`9:16/draft/jianying`。它描述承诺的产物类型，不把某个 `_v2` 路径固定为永久最新版本。

- video-and-draft必须同时满足视频/字幕契约和各画幅草稿；只执行过 `--formats jianying` 不得让视频从必需项消失。
- 文件名、主副版导出名、字幕方式及现有格式规则从当前有效配置解析；配置默认值只说明如何输出，不能凭默认值编造用户批准。
- 不用 `.cache/active-command.json`、文件mtime、最高 `_vN` 名字或目录遍历顺序决定最终契约及最新版本。
- decisions缺失或冲突时列明缺少的决定及配置差异，整单待核实；仍可展示有证据的已生成文件。已有明确来源不重复向用户询问。
- 新要求导致相关产物槽位或参数改变，保留旧契约和验收历史；现行清单仅以最新契约计算完整性。已取消的旧承诺进入历史，不作为当前缺项。

### 3.2 证据账本

`.wka/final-delivery.json` 包含 `version`、`contracts`、`artifacts`、`approvals`。记录逻辑上只追加，用现有原子JSON写入和工程写锁保护；不修改客户成片或外部草稿来存证据。

每条产物记录包含：唯一ID、稳定槽位、实际绝对路径、画幅/格式/字幕形态、生成或观察时间、文件/目录指纹、关联生成阶段与来源记录、按依赖组划分的输入快照、生成工具身份、来源覆盖边界。未知值如实为空并附原因，不编造旧生成时间。

验收记录包含：批准ID、既有步骤、审阅者/用户来源、时间、结论、审阅集合版本、绑定的产物ID及指纹、适用契约投影、直接验收或来源批准继承的证明。不能只凭步骤号、备注包含“通过”、进程退出码或文件存在判为当前已验收。

原始导出回执、人工修改后的磁盘快照、人工审阅结论分别保留。给手改草稿追加验收不改变 exporter 的 `.wka-complete.json`，也不让后续导出器把用户修改误当成可覆盖缓存。

### 3.3 只读核验与明确写入口

最终汇总纯函数只读取已存在文件和证据，不下载字体、不创建work目录、不运行用户脚本、不渲染、不刷新阶段账本、不迁移写回state。

可复用 `loadFilm` 的只读解析及 `evidence.mjs` 的内容指纹原语。读取进度直接解析JSON并在内存调用纯 `migrateProgress`；不能调用会写回旧flow的 `readProgress`。不能调用 `shotHashes` 或 `mainCheckConditions` 冒充只读检查：它们会准备工作目录和字体。

CLI `delivery --final` 明确只保存本次报告到 `review/最终交付清单[-画幅].json/.md` 及独立的 `review/最终交付审计[-画幅].json/.md`；不得借此补造批准、刷新来源证明或修改证据账本。报告保存失败要准确说明，不能宣称存档成功。

证据账本仅在以下明确写边界追加：最终产物成功生成并核验后；现有签批得到真实用户结论并成功绑定后；根据可验证历史建立只追加的迁移记录时。显式重试登记或历史迁移使用 `wka delivery ... --final --record`，只接纳已有可验证证据，不执行生成，不给无来源文件补签；不带该参数的查询不迁移历史。记录失败不能抹去成功生成的产物，但该产物显示“证据未存档，待核实”，可安全重试登记，不自动重导。

### 3.4 验收绑定与保存后变化

提交已有审片节点前，生成该节点的审阅集合及 `deliveryRevision`：包含确切产物身份/指纹、相关契约和来源投影。用户看到对应名称、画幅与版本，代理在真实回复后使用 `wka signoff ... --step N --delivery-revision <完整摘要>` 存档。

- 第13道绑定实际主版终审产物；第15道绑定实际交付草稿。只交视频时第15道的“无需草稿”仍是选择记录，不伪造草稿验收。
- 第14道沿用现有“先审副版小样、再出高清”流程。高清产物可凭已批准来源及实际生成/时间轴/字幕证据继承认可，清楚标为“来源已批准，高清生成核验通过”；不能宣称用户实际打开过高清。证据链不足则待核实，不自动增加新审片节点。
- 用户回复后到存档之间，产物或相关要求发生变化就拒绝沿用该集合，指出变化项。相同approval-id重试幂等；绑定集合不同不能覆盖旧记录。
- 不带新参数的旧signoff用法继续按原规则记录流程历史，但不能凭此生成新的逐文件验收证明。新director采用绑定参数，旧调用不会获得虚假“当前已验收”。
- 外部剪映草稿在用户保存并退出剪映后，绑定确切目录的完整普通文件清单与内容摘要；检测到仍运行、无法稳定读取或前后扫描不一致时提示处理对应阻塞，不存成成功验收。
- 初版不猜测某类native文件“只是缓存、可以忽略”。目录中普通文件的路径、大小和字节都参与；证据账本放在片工程 `.wka`，不放进被扫描草稿。链接或特殊文件无法完整核实则标待核实，不悄悄忽略或跟随到未知外部目录。
- 验收后摘要改变，显示“验收后磁盘文件变化，待复核”及变化文件；这不等于已证明画面语义变化。保留旧验收，保留用户编辑，只有重新验收当前版本才能恢复认可。
- 人工修改后的草稿不能沿用导出基线的技术结论：可核对的磁盘可读性、实际素材等重新核对，native显示和编辑语义由实际打开检查或明确用户反馈覆盖，记录其范围。原始source映射不足时单独说明“外部修改并验收”，不冒称与引擎源工程逐项一致；已知硬错误不能靠一条验收备注绕过。
- 文件指纹只证明磁盘字节身份。`not-tested`、`opened`、`playback-confirmed`仍由真实工具结果或用户反馈记录，不从hash、目录或阶段完成推断播放成功。

### 3.5 逐项依赖与过期

最终交付新增来源观察，不改 `runStage`、`sourceState`、`implementationState` 的缓存/恢复语义，不重写 `.cache/operations.json` 来让报告变绿。生成时登记明确的依赖路径、配置投影、实际字体/工具来源和覆盖范围；查询只读复核。

| 产物 | 最终交付应跟踪的相关输入 |
| --- | --- |
| 无字幕视频 | 对应画幅的镜头、共用脚本/素材、画面配置和时间轴；实际声音/终混；导出格式和相关编码实现 |
| 有字幕视频 | 无字幕视频依赖，加该画幅字幕原文/时码、英文、实际字幕版式/字体及烧录实现 |
| 独立字幕 | 对应语种的原文/时码、格式化实现及其已登记的生成或人工修订来源；不因纯字号变化使SRT过期 |
| 可编辑草稿 | 对应画幅镜头/时间轴、分轨声音、字幕原文/时码/版式/字体映射、草稿导出实现；手改后另绑定人工快照与审阅依据 |

画幅覆盖文件、主副版共用文件的影响分别计算；改英文字幕不让无字幕视频或中文字幕SRT连带过期。补充交付说明、修改清单排版、追加验收记录，不是作品输入变化，不能使所有交付物过期。

快照不能只存“某阶段signature相等”或全局仓库hash：需要能解释具体哪个相关输入发生变化。现有导出signature可作为生成链路旁证，不能代替当前逐项依赖比较。

自定义 `audio.build` 的现有缓存signature为null，用户镜头也可能执行任意代码；本设计不声称能静态推断任意JavaScript的全部文件/环境依赖。对已声明、实际记录的来源做有边界核验；无法确定的动态/外部来源、缺失字体来源、未知实现变化显示“来源覆盖不足，待核实”，说明缺口，不直接判当前有效或直接要求重渲。通过已有审片节点形成的人工版本认可仍须与机器来源覆盖分开显示。

报告显示每项的变化原因和影响，不保证本轮改变引擎实际重算次数。即使旧 `resume` 因全局来源变化显示stale，新最终报告也只能凭自身完整证据认定该项有效；缺证据时不能用“应该无关”绕过。

### 3.6 状态与用户入口

机器状态分开存储，避免一个stale吞掉所有含义：

- 可用性：存在且可读非空 / 缺失 / 不可读。
- 来源与检查：当前已核实 / 相关输入已变 / 证据不足；技术门槛通过 / 有据接受的软告警 / 确定错误 / 未核实。
- 验收：待验收 / 当前版本已验收 / 验收后文件变化 / 仅历史验收。直接验收和凭来源继承分别注明。

整单依最新契约聚合。必需项缺失、过期或存在确定错误为“未完成”；同时已有可用项时突出“部分完成 X/Y”。全部必需项已生成核实但尚需用户验收为“待验收”；全部当前且认可有效为“交付完成”；契约或证据不足为“待核实”，不得伪装完成。可选附录和历史材料的问题不阻断本次必需项。

面向用户的清单首屏只含：整单状态和统计；按画幅分组的必需产物；各项最新版本、状态和可用入口；阻塞原因、下一步动作与处理人；技术报告和完整审计附录入口。正常产物不展开依赖hash和原始日志。

最新当前产物即使尚待用户验收，也保留可打开的“待审文件”入口。过期、来源不明、验收后变化的文件在明确标注的“历史/待核实版本”区提供实际存在的路径，不混入“当前已验收”。没有文件时不生成虚假链接。宿主链接编码和generic原始路径规则沿用现有契约。

缺项不屏蔽其他有效项。下一步指明代理可处理的生成/核验任务，或用户需要完成的审阅、保存退出及缺失信息；不能把技术故障一律甩给用户。

最终JSON为version 2，包含契约、整体状态、必需项、历史项、阻塞与附录位置；各项保留原始绝对路径、指纹和状态原因。`ok=true`仅用于本次请求范围交付完整且验收有效；否则为false并返回退出码2，仍输出部分成果。参数/账本损坏/读取错误返回明确诊断；报告无法写入时返回1。不得把“报告写出”当成交付完成。

### 3.7 历史迁移

旧state、阶段回执和原始批准记录只读保留。查询可计算历史候选，但不补写新批准。

只有能建立“该次明确批准 → 当时确切产物或来源版本 → 当前内容一致 → 当前相关契约一致”的完整链路，才允许追加可追溯的继承证据。阶段完成记录加一段“草稿通过”文字不足以自动证明同目录当前内容已验收；同名、时间接近、最新mtime也不成立。

证据不足显示“历史已验收，当前版本待核实”，具体列出缺少的内容身份或关联。用户明确复核后可通过原有节点追加当前验收，不改旧history、不退回或伪造制作步骤。读取旧flow不得触发state写回。

## 4. 约束、兼容性与非目标

- 本轮只新增最终交付判定、展示和验收证据；不改渲染/混音算法、缓存复用条件、实际审片数量或制作流程编号。
- 不新增网页、播放器、云上传、外部数据服务或自动化任务；复用现有CLI、文件报告和宿主展示能力。
- 不自动覆盖、删除、移动、重命名、归档或重渲客户产物；不修改剪映native格式，不清理旧草稿。
- 保留用户编辑保护、同名避让和原始导出回执。手改草稿验收通过，不授权后续导出覆盖该目录。
- QC软告警的接受沿用既有归属、范围、理由和来源绑定；保留原测量。不能把人工接受写成机器全通过，不能绕过硬错误。
- 历史/可选材料仍可追溯；精简展示不能靠删除文件、抹掉失败历史或隐藏必需项实现。
- 安装扩展、资源预算、bundler缓存、等待心跳、音乐审听执行、画风和母带一致化均不在本批。

## 5. 错误处理与运维

账本/decisions格式错误、来源冲突、同一批准ID绑定变化、目录不稳定、不可读、缺证据分别报出实际对象和处理方式。账本损坏不得回退成“空记录因此完成”；保留原文件，不自动重建或清空。

报告及账本原子保存；批准绑定失败不提交虚假的成功验收。重试同一批准必须核对原集合，追加记录幂等。只读核验不能执行用户代码来补齐证据，也不能因字体缺失自动下载。

发生失败时仍列出可安全展示的已核实成果。新清单不以旧报告当本次成功，不依靠未确认的mtime猜测版本。旧报告、原始记录及用户文件保持可回溯；回滚插件只停止生成新证据，不清理新增账本或改写旧工程。

## 6. 验收标准与测试

| 编号 | 可验证的通过条件 |
| --- | --- |
| A1 契约稳定 | 先视频后草稿、最后运行qc/其他命令，必需项仍按确认契约包含所有视频/字幕/草稿；未知/冲突列明，单画幅结果不宣称全片完成 |
| A2 清单精简 | 构造2044项含大量抽帧的目录，主清单只展示当前契约产物及阻塞/附录；完整审计仍可查，历史试听过期不阻断当前整单 |
| A3 部分可用 | 视频当前、草稿缺失时仍提供视频入口，整单部分完成并返回2，列明缺项、原因、下一步和处理人；不可读/缺失路径不伪造链接 |
