## 1. 问题与目标

用户要求审核插件的代码质量、性能和架构，并确认优先处理制作失败、结果错误和返工，以分批改进为主。第一批只修复下列三个已静态核对的边界；本轮尚未执行缺陷复现，不把静态结论记为测试通过。

| 编号 | 已核实的事实 | 已确认的目标 |
| --- | --- | --- |
| R1 | `core/job.mjs` 的 `loadFilm` 校验字段格式和镜头文件，但不拒绝重复 `shot.id`；缓存用 ID 作键，`ShotCache.store` 会删除该键的旧文件。两个同 ID 镜头起点不同、哈希不同，后完成者可删除前一片段，后续产物登记或拼接失败。 | 加载时指出重复编号，在启动渲染和写入镜头缓存前拒绝。 |
| R2 | `core/cache.mjs` 直接覆盖 `manifest.json`，构造时直接解析 JSON。写入中断后若留下截断清单，原命令重跑和 `--force` 都会在缓存构造时失败。 | 原子保存清单；损坏清单可诊断并允许重新生成缓存，保护素材、声轨和已签批文件。 |
| R3 | `core/project.mjs` 在仓库尚无 HEAD 时执行未限定路径的首次提交，会夹带用户先前暂存的无关文件。 | 初始化提交只包含本次初始化应提交的文件，保留用户无关文件的暂存状态和工作区内容。 |

三项作为用户明确选择的同一修复批次管理，但各自验收，不引入跨模块新框架。依据为本次 grilling 的 Q1–Q3、Q7 及用户最后的“确认”；第二、三批另行形成规格。

## 2. 架构与组件边界

| 组件 | 本批职责与边界 |
| --- | --- |
| `plugin/engine/core/job.mjs` | 在共享的 `loadFilm` 入口做镜头 ID 唯一性校验，使主副版、browser 与 Remotion 共用同一规则。 |
| `plugin/engine/core/cache.mjs` | 负责清单完整读取、损坏降级、原子保存和原有缓存命中行为；只恢复可再生的镜头缓存索引。 |
| `plugin/engine/core/evidence.mjs` | 复用现有 `atomicJson` 原语；不重新实现一套全局存储框架。 |
| `plugin/engine/core/project.mjs` | 收紧无 HEAD 时的初始化提交范围，保留现有身份检查、忽略规则维护和已有提交分支的行为。 |
| 自动化测试 | 分别验证入口拒绝、损坏恢复和真实 Git 暂存区保护；已有渲染与恢复用例承担回归。 |

沿用现有制作写入互斥、阶段账本、视频校验和签批机制。缓存索引恢复不修改这些机制，也不能为产物补发签批或证明媒体已经有效。

## 3. 接口、数据与行为

### 3.1 R1：重复镜头编号提前拒绝

- 继续由现有 Schema 检查 `id` 格式，随后在 `loadFilm` 内检查整个 `film.shots` 的 ID 唯一性；不是检查镜头对象是否完全相同。
- 同一 ID 出现两次或以上即拒绝，不因文件名、镜长、画幅或渲染管线不同而允许重名。不自动重命名、合并或丢弃镜头。
- 错误必须指出重复编号，便于用户定位 `film.json`；调用方沿用当前失败返回路径，不引入新 CLI 参数。
- 校验覆盖 `requireShots: false`，因为允许镜头文件尚未存在不代表允许编号重复。
- 校验完成前不得启动浏览器、渲染/编码进程、准备字体或写入镜头缓存。CLI 既有锁和失败记录可按现行规则处理，不把入口失败解释为整个命令绝对零文件写入。
- 唯一 ID 工程的镜头顺序、文件选择、缓存键和哈希规则保持原有语义。

### 3.2 R2：缓存清单原子写入与损坏恢复

- 保持现有 `manifest.json` 路径与 `{ shots: { ... } }` 数据布局；已有有效清单可继续读取，不要求整体缓存迁移。
- `store` 与 `invalidate` 的清单保存使用现有 `atomicJson`：先写同目录临时文件，再替换正式清单。进程写入中断不应把原有有效清单覆盖成半份 JSON。
- 清单不存在时按现行空缓存处理。空文件、截断 JSON，以及无法作为现有清单解释的结构不得作为命中证据；报告原因后按未命中处理，允许原命令继续重渲。
- 诊断至少包含受影响的清单路径、损坏原因与“缓存索引失效，相关镜头需重新生成”的说明。不得把降级恢复报告为缓存命中或技术验收通过。
- 权限、目录访问或磁盘写入错误不冒充清单损坏；明确报错，不能在无法保存时宣称恢复成功。
- 降级不清空整个 `.cache`，也不按损坏条目中的路径删除文件。有效记录的正常缓存淘汰保持现有边界；不从失去索引的片段猜测可复用性。
- 只处理当前主版或副版对应的缓存目录，不能顺带重置另一画幅的索引。
- 素材、声音文件、`.wka` 进度与签批记录、`.cache/approved` 快照、审片文件和既有成片不因清单恢复被删除或改写。正常重渲仍执行原有媒体检查。
- 本批保证进程中断情况下的完整文件替换及损坏后可重跑，不新增跨设备事务或断电持久化保证。

### 3.3 R3：首次提交不夹带用户暂存内容

- 在已初始化但尚无 HEAD 的仓库中，初始化提交范围限定为本次维护的 `.gitignore`，不能提交整个暂存区。
- 所有与该 `.gitignore` 无关的既有索引条目保留原路径、内容与模式；无关工作区文件的内容也保持不变。
- 覆盖“文件已暂存，随后又修改工作区”的情形：提交后仍保留原已暂存版本与工作区版本之间的差异，不用重新 `git add` 无关文件恢复状态。
- 全新空仓库仍能正常初始化并创建仅包含 `.gitignore` 的首次提交。已有 HEAD 时的忽略规则更新和用户修改保护继续沿用现有行为。
- 缺少 Git、缺少身份或提交失败时保留现有可读提示；失败不得造成无关文件被提交、重置或丢失暂存内容。
- 不新增自动提交其他工程文件的行为；后续审片快照的范围不是本批重设计对象。

## 4. 约束、兼容性与非目标

- 本批不改变生成画面、帧率、声音、字幕、主副版关系或审片门槛。
- 对此前被接受的重复 ID 配置明确报错，这是 R1 的预期修正；不提供绕过唯一性检查的兼容开关。
- R2 允许损坏索引导致相关镜头重新生成，以正确性优先；不承诺修复索引后保留原有缓存命中率。
- 使用临时测试工程验证，不修改客户作品、已安装插件缓存、既有签批成片或外部剪映草稿。
- 本批不修改依赖安装流程、流程版本迁移、剪映 CI、性能算法或渲染并发；这些属于已确认的后续批次。
- 近期继续使用 browser/Remotion，不新增 Manim/Blender，不拆分整个核心，不为未来管线建立通用框架。
- 第三批先测长片、大音轨、无改动重跑与只改单镜，再决定优化重复哈希还是同步校验；具体收益数值待基准测量，不阻塞本批。
- 规格初稿阶段只交付本文；获批后实施第一批三项修复，不包含版本发布或安装升级。

## 5. 错误处理与运维

R1 错误属于输入配置错误：应提示修正重复编号后重跑，不提示用户清缓存或重装插件。

R2 降级属于可再生缓存索引失效：说明重渲原因，不要求用户删除整个 `.cache`。保存失败应保留可诊断的实际错误；不能以成功日志掩盖未落盘结果。原子写入是对现有缓存清单保存方式的局部修复，不扩大自动清理权限。

R3 的 Git 提交结果必须以实际退出状态为准；初始化失败或跳过提交不应破坏用户原暂存内容。诊断不输出无关文件正文。

三个模块均沿用现有失败传播和恢复入口，不新增后台重试、不改变用户签批记录、不自动推进制作工序。

| 验收项 | 场景 | 必须证明的结果 |
| --- | --- | --- |
| A1 / R1 | 两镜同 ID，但文件、时长或内容不同；另测完全相同的重复项 | 明确指出重复 ID；尚未启动渲染或写入镜头缓存即失败。 |
| A2 / R1 | `requireShots: false`、主副版、browser/Remotion 配置 | 同一唯一性规则生效；合法的唯一 ID 配置继续通过。 |
| A3 / R2 | 空清单、截断 JSON、无法解释的清单结构 | 给出可定位诊断；原命令不再卡在 JSON 解析，可重新生成有效片段和清单。 |
| A4 / R2 | 在正式文件替换前注入保存失败；正常完成保存 | 失败时原清单仍完整可读，成功时得到完整的新清单；`store` 和 `invalidate` 均覆盖。 |
| A5 / R2 | 在隔离工程中损坏一个画幅的清单并真实重跑短片渲染 | 新片段通过现有媒体检查；另一画幅索引、素材、声音、进度、签批快照、审片文件与既有成片保持不变。 |
| A6 / R2 | 正常缓存命中，以及读取或写入权限失败 | 有效缓存仍复用；访问失败明确报错，不伪装为成功恢复。 |
| A7 / R3 | 已 `git init`、无 HEAD，预先暂存一个无关文件；该文件再产生未暂存修改 | 新提交只含 `.gitignore`；无关索引条目的内容和模式，以及工作区内容与分层差异，前后一致。 |
| A8 / R3 | 全新仓库、已有 HEAD、缺少身份及提交失败 | 正常初始化和已有保护行为不回退；失败/跳过时无关暂存内容仍保留。 |

测试按“先运行失败用例确认原始症状，再最小修复并运行通过”的顺序执行。R1/R2 使用实际入口和隔离文件系统，R3 使用真实临时 Git 仓库核对提交树和索引，不以源码字符串断言代替行为验证。

实现阶段先执行定向回归，再执行仓库 `npm test`、`npm run smoke`、`npm run lint` 和 `git diff --check`。视觉基准不因本批修复更新；缺少依赖的跳过项单独报告，不算通过。远端 CI 与本地结果分别记录。
