## 结论

流程最终交付成功，但客户承担了本应在提交审片前发现的技术检查：文件能否打开、字幕是否遮挡，以及后半段声画是否同步。最需要优先修的是时间轴与输出帧数的一致性；再把关键词同步、字幕检查和审片交付做扎实。单纯增加签批节点解决不了这些问题。

## 源码核验与诊断

### 1. 时间轴仍有累计误差入口（最高优先级）

- `plugin/engine/core/job.mjs` 的 `loadFilm` 用未量化的 `duration` 累加 `start`；拼接采用 `-c copy`，没有按统一时间轴校验每个切点。
- `plugin/engine/pipelines/remotion/entry.mjs` 用 `Math.round(seconds * fps)` 为每个镜头独立分配帧数。历史代理所说的“向上取整”不是当前入口的完整描述，当前是独立四舍五入，也可能累积偏移。
- `plugin/engine/pipelines/remotion/index.mjs` 先按 film.fps 渲染，再对每个镜头用 ffmpeg `fps=job.fps` 降帧；独立转换又引入一层量化。
- `plugin/engine/core/qc.mjs` 用计划 `start` 归属镜号，未先核对实际切点。故会话里的“镜号偏一个”可能受时间轴漂移影响，不能据此认定存在固定减一错误。

只读诊断结果：

| 用例 | 结果 | 结论范围 |
| --- | --- | --- |
| 31 帧、30fps 的临时视频，经当前相同 `fps=15` 过滤器转换 | 原片 1.033333 秒，转换后 16 帧、1.066667 秒 | 实际运行 ffmpeg/ffprobe，证实逐镜降帧可延长时长 |
| 107 镜，每镜 1.02 秒，用当前 `buildEntry` 分配帧数 | 计划 109.14 秒；高清合计 3317 帧，即 110.566667 秒 | 直接调用生产纯函数，证实独立舍入可累计偏移 |
| 上述每镜再按已测 31→16 帧转换计算 | 小样预测 114.133333 秒 | 计算推导，未实际渲染 107 镜，不是客户成片测量 |
| 客户最终 film.json | 107 镜、计划 241.2 秒、主版合计 7236 帧，全部镜头帧数为偶数 | 当前项目已落在 15fps 网格，规避此问题；不是引擎普遍正确的证明 |

### 2. 主版保护存在重复检查成本

`core/approval.mjs` 的 `checkMainUnchanged` 始终把当前哈希与签批哈希比较。共用脚本改过、但主版输出没有变化时，每次副版命令都会再次进入渲染调度和 PSNR 比对。渲染可能命中缓存，不能笼统说每次都重渲全部镜头；逐帧比对结果确实没有复用记录。

`bin/wka.mjs` 的 `cmdFinal` 在区分输出格式前先终混、渲染与拼接，纯草稿输出也会走这些阶段。是否可跳过某阶段必须按输入变化验证，不能为提速牺牲正确性。

### 3. 已有规则与能力应加强执行

- director 已有“全程用用户语言”“交付绝对路径”“用户已说清不再问”的要求；无需再添加相互重复的规则。
- keynote STYLE.md 已有双语字幕安全区；默认字幕仍为白字、半透明黑描边。应先验证亮背景效果，不能把客户片子的样式补丁照抄成所有风格默认值。
- 当前已有持久依赖解析，以及剪映运行检查与同名草稿避让，应保留。
- 闪烁和硬切告警是画面差异检测，不能据此自动认定是误报或已通过。对实际问题、人工接受的设计、待检查项分别记录理由与时间段。

## 优先级与交付顺序建议

1. **P0：可靠时间轴。** 覆盖主版/副版、高清/小样的切点与总帧数；给 QC 增加同步偏移检查。先补失败回归用例，再修根因。
2. **P1：审片前发现内容问题。** 关键词按实测 cue 出现；字幕保护术语，检查双语安全区与白底可读性；明确机器检查和人工抽查的边界。
3. **P1：等待与恢复可信。** 安全复用主版比对，输出阶段与画幅清楚；中断先检查产物，已有授权范围内连续执行，真实审片节点仍等用户。
4. **P2：减少沟通返工。** 链接交付、参考素材单独询问、配乐段落审听、草稿差异披露形成具体检查项。

实施顺序及范围待 PRD 批准，以上均不代表已实现。
