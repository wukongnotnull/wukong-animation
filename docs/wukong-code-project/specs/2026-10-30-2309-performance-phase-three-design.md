# 第三批性能优化：测量基线、有界哈希与状态扫描去重

Status: Draft — pending user review
Date: 2026-10-30 (Asia/Shanghai)
Spec approval: Pending

基线：`5957b73e90f014011fb27d3e015d4987c39db6ba` / 插件 v0.19.3。跟踪 [#113](https://github.com/wukongnotnull/wukong-animation/issues/113)。用户本轮要求“继续第三批性能优化，先整理规格与实施计划”，因此同时提供规格和计划草案；尚未批准实现，不修改制作代码或发布版本。

沿用已确认的可靠性优先、小步改进和第三批先测量再优化的顺序。已有 v0.19.0 低负载预览不重做，v0.19.2 / v0.19.3 的失败恢复、依赖锁定和流程保护必须保持。

## 1. 问题与目标

| 编号 | 已核实事实 | 本批目标 |
| --- | --- | --- |
| P1 基线 | 历史性能报告只测了 107 镜工程的前 6 镜、10.9 秒、无混音，每场景一次，未运行长片矩阵；不能外推长片、大音轨或完整交付速度。仓库没有持续可重复的性能测量入口。 | 建立隔离、可复跑的长片/大音轨/首次/无修改/改单镜基准，区分哈希、校验、渲染和编码开销。 |
| P2 内存 | `evidence.fileDigest`、`timing.fileSha`、`cache.hashParts` 的文件分支及 `final-delivery.deliverySnapshot` 均将文件整体读入 Buffer 后哈希。 | 保持哈希语义，使用有界分块读取，使读取缓冲区不随媒体文件体积增长。 |
| P3 重复读取 | `operations.sourceState` 先读取声明的镜头/音频文件，再遍历 shots/audio，同一文件重复计算内容摘要。隔离 107 镜样本中每镜与音轨均读取两遍。 | 只在单次同步 sourceState 观察内复用已经计算的内容摘要；保留全部声明、路径、顺序与缺失语义。 |

初步诊断：在 M1 Pro / Node 25 上，256 MiB 文件单次哈希读取请求为 256 MiB；sourceState 一次逻辑读取约 512 MiB，读取后采样的 Node RSS 增量中位数约 519 MiB。详情与边界见[诊断记录](../reports/2026-10-30-performance-phase-three-diagnostic.md)。这是合成二进制、无渲染的诊断，不是端到端基准或已经实现的提速。

同步 ffprobe、实现目录/系统字体扫描、多个交付槽位反复观察输入也值得测量；当前没有足够端到端证据将它们列为本批改造对象。特别是 deliverySnapshot 的两遍读取用于发现扫描期间变化，不能直接删除第二遍。

## 2. 架构与组件边界

| 组件 | 职责与边界 |
| --- | --- |
| 开发测量工具、隔离夹具 | 只在明确执行基准时启动；记录源码版本、环境、输入、工作量和结果，不进入日常制作流程。诊断计数与正式计时分开运行。 |
| 建议新增 `core/file-hash.mjs` | 仅实现同步、顺序、固定缓冲区的文件哈希；不判断产物通过、批准、阶段复用或工程版本，不保存跨调用缓存。 |
| evidence / cache / timing / final-delivery | 保留各自数据契约和校验职责，将用于哈希的整文件读取替换为共享原语。JSON 解析、脚本加载等需要文本的读取不属于本批。 |
| operations.sourceState | 创建并销毁自己的摘要观察上下文，声明引用与目录遍历共享它；其他调用者默认仍重新读取文件。 |
| 现有 CI | 继续完整回归、视觉冒烟、严格剪映和三平台分发；在现有三平台任务中增加不依赖媒体工具的哈希/状态观察单测，核对文件读取边界。增加确定性的字节/缓冲区/读取次数断言，不用共享 CI 的墙钟波动作硬性速度门槛。 |

选择同步分块接口以保留当前同步调用链，减少改造面。它主要控制内存并减少重复工作，不等于异步、不消除事件循环阻塞，也不承诺 ffprobe 检查时间下降。只有后续测量显示值得改变接口时，再为异步校验或命令级观察提出独立规格。

## 3. 接口、数据与行为

### 3.1 P1：先建立可复跑基准

拟新增开发命令 `node tools/bench-performance.mjs --engine <engine目录> --suite <hash|workflow> --rounds 5 --out <新输出目录>`。这是批准后实现的接口，目前尚不存在。

- engine 必须含可验证的清单与锁，比较双方使用同一 Node、锁定依赖、Chromium、ffmpeg/ffprobe 和字体；记录解析后的依赖身份、工具版本、平台、架构、CPU、内存及 worker 配置。
- 从明确 Git 提交的干净副本执行基线和候选，运行时/测量工具摘要均入报告。两边独立缓存、临时 HOME 和临时剪映目录，素材字节与工作量一致；不使用客户工程或现有签批目录。
- 测量前准备好依赖/字体，准备时间单列，不混入制作耗时。记录“制作缓存未建立”与“制作缓存已建立”，不将它们误称为操作系统文件缓存冷/热；不清理系统缓存。
- 每个场景至少 5 个有效样本，串行、交替基线/候选顺序，保存所有结果、范围与中位数。超时、失败和缺依赖单独计数，不能删掉异常样本后声称通过。单次超时有限，工具关闭自己启动的进程。
- 无修改、改单镜场景各自从相同的已完成基准缓存副本开始，不能让上一轮修改影响下一轮。镜头源码修改应保持画面复杂度相同，并确认只重渲一个镜头；无修改须确认零重渲。两边比较相同命令，不把 preview 与整片 render 的差别当作本批加速。

| 组别 | 夹具与场景 | 必须记录 |
| --- | --- | --- |
| 哈希与状态 | 8/64/256 MiB 确定字节文件，107 个镜头源码，声明音轨也在 audio 树中；hashFile、sourceState、deliverySnapshot 分开运行 | 内容摘要、逻辑读取字节、最大读取缓冲区、每文件哈希次数、Node 内存、CPU与耗时；双遍快照仍为两遍 |
| 代表短片 | 仓库《春江》前 6 镜的独立副本及《七十二变》4 镜原例，实际时长由清单计算并记录；browser/Remotion 各一组 | preview 与 render --proxy 各自首次、无修改、改单镜；实际输出规格、生成帧数、重渲镜数、是否整片编码 |
| 长片 | 自包含的 browser/Remotion 各 107 镜，2.05 秒/镜、219.35 秒，固定简单画面、512×288、30fps 原规格，小样按既有规则生成 | 同上；这是镜头数量/时长压力，不代替复杂艺术镜头的真实制作时间 |
| 大音轨 | 长片使用有效 PCM WAV；48kHz/双声道/16bit 覆盖片长，另给出 256 MiB 长音轨，播放区间明确且两边完全一致 | 音轨字节、被重复哈希次数、对应预览时间段；不使用诊断中的伪 WAV 充当真实媒体 |
| 校验边界 | 已完成长片的 `resume`、QC、`delivery --final`；夹具生成所需证据，但不伪造用户批准 | 哈希/读取、ffprobe 全帧检查次数与 CPU；技术结果与签批状态一致。resume 不新增制作产物，delivery --final 只更新既有报告文件，核心 finalDeliveryReport 保持只读 |

资源指标至少包括墙钟、CPU、主 Node 进程内存口径。若记录进程树合计 RSS，必须明确采样间隔与漏采可能；没有进程树指标时不能把单进程 RSS 说成整套制作的峰值。计数探针会增加开销，因此带探针的运行只用于归因，正式耗时比较使用不带探针的运行。

基准报告先给出观察到的耗时组成和重复工作。P2/P3 先有这些基线再改；如果主要耗时来自解码或渲染，只能报告有限的哈希/内存收益，不能临时扩大为并发/异步改造。

### 3.2 P2：固定缓冲区、保持哈希字节契约

- 共享原语建议提供 `hashFile(file)`（SHA-256 hex）与 `updateHashFromFile(hash, file, options)`（把原文件字节依次喂入已有 hash，返回读取字节数）。最终命名可在同一职责内调整，不增加用户配置。
- 使用不超过 1 MiB 的可复用读取缓冲区，按实际 bytesRead 更新；短读继续、EOF 正确结束，禁止将多块再拼回完整 Buffer。描述符在成功和所有错误分支中关闭，不增加文件级并发。
- `fileDigest` 的既有同步返回值保持不变；稳定文件的新旧 SHA-256 必须完全相同，包括空文件、二进制、非整块大小、含中文和空格的路径及当前用到的 file URL。
- `hashParts` 保持文件名、原始内容长度、原始字节、部件顺序、分隔符、缺失标记和最终截断规则；不能把文件的 hex 摘要替代原文件字节输入。相同内容换安装目录仍得到相同哈希；两个文件互换内容仍不同。
- 文件大小与内容观察来自同一次打开；读取前后核对文件身份/大小/可用的高精度修改信息，路径被替换、截断或读错时明确失败，不能发布部分内容的成功证据。普通缺失/I/O 错误沿用调用者现有处理，不统一吞掉。
- deliverySnapshot 保留拒绝符号链接/特殊文件、目录排序、空目录判定、完整目录覆盖和两次独立扫描比较；只改变每次读取的内存方式。两个扫描不能共享摘要结果。
- checkedVideo 的内容检查、检查后再次读内容确认、fresh 语义、ffprobe 版本与完整帧时间戳检查保持；前后读取不能被摘要复用折叠。仅替换其私有 fileSha 的读法。
- 不改变持久化证据/缓存 schema、FLOW、TIMING_VERSION、包版本或依赖锁。实现摘要包含代码本身，代码变化引起既有逻辑的一次安全失效可以发生，不能据此绕过实现身份检查；稳定输入的数据摘要本身应兼容。

### 3.3 P3：单次 sourceState 内去重

- 对外 `sourceState(dir)` 仍同步返回现有格式的 hex 摘要。每次调用创建新上下文；返回或报错后立即丢弃，不在进程全局、磁盘或工程文件中缓存。
- 声明引用和 shots/audio 遍历保留原数据结构、顺序和路径条目，仅对同一次观察内 `path.resolve` 相同的文件复用已计算摘要。不能删掉“重复”的语义条目，不能按文件名合并，也不跨不同符号链接/硬链接路径合并。
- 去重范围仅为内容哈希；为解析 film.json 的单独文本读取不必合并。treeEvidence/fileEvidence 的默认行为和其他调用者不改变；可用显式可选读取器或局部包装接入，禁止全局替换 fs 或默认开启进程级缓存。
- 首次读取得到真实内容摘要；复用前及观察结束核对文件身份和修改信息。变化或无法核实时使该次观察失败，不用旧值补齐。元数据只作为这一次同步观察内的变化检测，不能当作跨命令的内容证明。
- 下一次 sourceState 必须重读，即使文件长度相同或用户恢复 mtime。阶段执行前后、任何 await/外部制作、签批和恢复调用之间不得共享这个上下文。新增/删除/重命名文件必须在下一次调用反映出来。
- 缺失声明、audio/generated 排除、目录遍历和跨画幅输入的既有语义保留。无法保证稳定观察时不写 completed 记录，也不能把未知来源认作通过。

### 3.4 收益与放行标准

硬性结构指标：大文件哈希最大读取缓冲区不超过 1 MiB；在固定 107 镜/单音轨夹具中，单次 sourceState 每个被重复引用的文件只做一次内容哈希，音轨逻辑读取从 2N 降为 N；交付双遍扫描仍为 2N。这些指标是拟议验收条件，不是当前实现结果。

墙钟收益须由配对基准报告，不承诺倍数。任一有效场景候选中位数相对基线增加超过 `max(100ms, 基线的10%)` 时暂停放行，检查环境和归因并按相同方法复测；仍有回退则缩小/回退该项改动，不放宽阈值掩盖。这个容差是本草案提出的验收选择，待用户随规格批准。

若时间差落在波动范围内，但有界内存和读取量确已改善，可如实以该收益交付，不能称为端到端显著提速。每项报告收益、增加的 stat/系统调用代价及未验证场景。

## 4. 约束、兼容性与非目标

- 画面、声音、字幕、累计帧切点、画幅、终稿品质、小样规格、worker 默认值和既有 CLI 含义保持不变。
- 完整解码检查、交付双遍扫描、用户签批、未知来源阻断和较新流程写入保护不得减少或绕过。
- 本批不新增全局或磁盘摘要缓存，不用 mtime/size 代替跨调用的内容核对，不跨 await/写入复用观察。
- 不新增渲染管线，不增加并发，不默认使用硬件编码，不升级依赖，不整体异步化，不做无证据的大规模重构。
- 所有测试和基准使用可确认归属的临时副本；不修改客户作品、已安装插件缓存或真实剪映草稿，不清理系统缓存与旧依赖。
- 本轮只提交规格、计划与诊断证据；实现须另获规格批准，合并/发布/安装升级不在本轮范围。

## 5. 错误处理与运维

文件不可读、读取中断、内容变化、目录增删或工具失败必须保留可诊断原因。共享哈希原语抛错，由当前调用者决定报错或缓存未命中；不能把整个工程降级为“未初始化”。内部缓冲区或观察 map 出错时不登记成功阶段/批准，也不删除源文件或既有产物。

基准输出必须包含失败阶段和退出状态；输出目录非空且无法确认归属时拒绝覆盖。超时只终止本次启动的进程，清理只删除本次临时资源。比较报告明确代码版本、是否带探针、依赖/制作缓存状态和实测范围。

## 6. 验收标准与测试

| 验收 | 场景 | 必须证明 |
| --- | --- | --- |
| A1 | 两条管线短片/107 镜/大音轨，首次/无改/单镜 | 至少 5 轮同命令配对测量，结果/失败完整记录；无改 0 镜、单改 1 镜；不能把不同工作量比较为提速 |

| A6 | 相邻两次调用同长度改写并恢复 mtime；增删/改名/阶段写入 | 第二次重新读取并改变摘要或明确失败，不跨调用/await 复用旧观察 |
| A7 | sourceState 观察期间文件/身份变化 | 当前观察拒绝，无完成/批准记录；默认 treeEvidence 调用者不受局部去重影响 |
| A8 | 最终交付单文件/目录，两次扫描之间变化或链接 | 仍有两遍真实读取，变化/特殊文件拒绝，旧签批失效判定和报告只读性保持 |
| A9 | 视频内容/期望/工具变化，损坏证据，完整检查 | 重新检查且不能沿用旧成功；检查前后内容比较仍独立；帧数/逐帧时间戳/容差不放宽 |
| A10 | 旧流程/未来流程、损坏缓存、依赖身份、镜头冲突 | 前两批回归和当前制作/签批/恢复用例通过，force 不能绕过流程保护 |
| A11 | 性能与资源对比 | 满足缓冲区/读取量硬指标；按 3.4 检查回退；内存口径清楚，无未经测量的整片提速宣称 |
| A12 | 完整验证与打包 | npm test、严格剪映、9 张视觉样张、长片时间轴矩阵、三平台纯文件 I/O 单测、lint、便携构建和当前提交 CI 通过；不更新视觉基准 |

实现采用失败测试 → 确认失败 → 最小修改 → 通过的顺序。现有两遍扫描故障注入如依赖 readFileSync，应改到实际读取边界注入相同故障，保留“变化必须拒绝”的断言，而不是删除测试。

本草案阶段只执行了隔离诊断和 32 项相关既有基线测试（全通过、零跳过）；没有执行新基准、完整长片或优化后对比，没有实现 P1/P2/P3。

## 7. 依据与审阅重点

仓库依据：`core/evidence.mjs`、`core/operations.mjs`、`core/cache.mjs`、`core/timing.mjs`、`core/final-delivery.mjs` 及既有 [v0.19.0 性能报告](../reports/2026-10-30-render-performance.md)。Node 20 支持显式缓冲区读取与多次 hash.update，接口依据为 [fs.readSync](https://nodejs.org/docs/latest-v20.x/api/fs.html#fsreadsyncfd-buffer-offset-length-position) 和 [hash.update](https://nodejs.org/docs/latest-v20.x/api/crypto.html#hashupdatedata-inputencoding)。采用同步有界读取是本规格的设计选择，不把它描述为官方推荐的整个制作架构。

请重点审阅：先测基线再改的顺序、仅 sourceState 内去重的范围、保留交付双遍和完整解码的代价，以及性能回退容差。实施任务见[计划草案](../plans/2026-10-30-2310-performance-phase-three.md)。
