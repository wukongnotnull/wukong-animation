# 阶段进度与中断恢复（FR-6）

Status: Draft，待用户审阅本文件；不是实现许可。
日期：2026-10-29；基线：main `d370839`。
依据：[已批准 PRD](../prd.md) FR-6、[issue #93](https://github.com/wukongnotnull/wukong-animation/issues/93)。依赖 FR-5 的主版检查结果，向 FR-7 提供已确认产物。

## 1. 问题与目标

现有 `state.json` 只记录工序与签批历史，不能说明正在执行哪个画幅的哪项计算。`cmdFinal` 在划分格式前统一混音、渲染、拼接；剪映每次使用新名字，恢复重跑可能产生重复草稿。`signoff` 先写 history 再生成审批快照，失败时可能留下部分完成状态。

目标：日志和状态准确解释等待；恢复先验产物，再决定复用或补做；已完成的外部导出不重复创建，明确的用户批准可以继续存档，待审节点继续等待。

## 2. 架构与组件边界

- 新 `core/operations.mjs` 记录机器阶段与产物回执；CLI 负责按当前命令组织阶段，不建立后台自动制作服务。
- `.wka/state.json` 继续记录工序、用户结论与定稿身份；`.cache/operations.json` 保存当前执行记录及产物签名。剪映任务在片内 `.wka/export-receipts/` 保留可恢复回执，允许随工程备份；不把外部草稿材料纳入 Git。
- `job.mjs` 将逐镜素材准备与全片拼接分开；原 render 命令仍输出拼接视频，纯剪映 final 只准备所需片段/时间线。音频准备继续生成导出所需的实际分轨，不跳过来源刷新。
- `wka resume <片目录> [--json]` 只检查并输出恢复建议；继续计算由原命令重跑完成。director 依据已授权需求执行建议，不把旧工序号当新授权。

## 3. 接口、数据与行为

### 3.1 阶段与复用

阶段标识固定为 `main-check`、`soundtrack`、`segments`、`concat`、`subtitle-preflight`、`subtitle-burn`、`encode:<format>`、`draft-export`。每条日志带画幅、主/副版、小样/高清、阶段名和状态（开始/复用/完成/失败）；主版检查嵌套在副版任务时明确当前计算的是主版。

记录包含 `version:1`、操作 id、命令参数、输入签名、每阶段状态、起止时间、输出路径/内容 SHA-256、错误摘要。阶段开始和完成原子保存；没有完成回执不能直接当完成。stdout 人类可读，`resume --json` 提供同一事实，不从日志反推成功。

签名按实际依赖构建：声音配置/原录音/配乐脚本及其本地输入/相关风格与处理代码；镜头用当前渲染哈希与时间轴；字幕用现有预检签名；编码包含实际音视频字节、编码设置与导出器代码；草稿包含全部片段/分轨/字幕/样式、目标根目录及写入器/字体映射版本。不能证明依赖完整的动态音频脚本不复用其准备阶段，下游仍可按实际文件字节判断。

输出存在、完整、签名相同且媒体/草稿结构有效时才复用；修改、删除或损坏的产物补做相应阶段。时间轴与字幕门槛仍校验当前证据。`--force` 明确重做该命令产物；剪映强制导出仍同名避让，不覆盖旧草稿。

纯 `--formats jianying` 不拼全片、不烧字幕、不编码 MP4、不复制无关外挂 SRT；仍准备实际分轨、镜头片段、字幕与主版保护证据。草稿的片段帧数逐镜验证，不能拿“没拼接”作为跳过 FR-1/FR-2 的理由。草稿字幕需验证文本/时间/样式，不能把未生成的全片预检报告写成已通过；成片已定稿时可引用当前成片预检证据。

### 3.2 外部草稿的中断窗口

创建前记录操作 id、确定的新草稿路径和计划签名。Python 写入器在本次草稿内写同操作 id 的完成回执，最后发布完成标记；片内回执随后登记实际路径、文件清单与哈希。恢复时先用两处回执对账，覆盖“草稿已写完，但 CLI 还没记成功就中断”的窗口。

- 回执一致、内容完整且未改：返回原路径，不创建 `_v2`。
- 已完成回执存在，但用户编辑了草稿：标为 `user-modified` 并列原路径，**不自动覆盖或重导**；已完成导出事实保留，要求用户明确选择是否另导新版。
- 只有准备记录：只检查记录指向的确切路径，不扫描名字猜测所有权。能证明本次写入完整则补登记；可证明为本次未完成草稿时清理本次临时产物后重试。
- 无法判定所有权或是否完整：标为 `needs-review`，不删除、不自动再导；展示路径与不确定原因。
- 剪映运行检查、草稿目录检查和旧草稿保护仍有效。纯复用不写外部草稿，可报告现有结果；需要写入时才检查是否退出。

### 3.3 签批存档恢复

`signoff` 只在用户已经明确批准后调用。接收可选 `--approval-id <id>`，同一条用户批准重试沿用同一 id。先保存待提交记录（工序/画幅/结论/产物签名），检查当前技术门槛并准备快照，成功后一次写入 history 与 approval；Git 提交失败单独记录，不撤回用户结论，也不再询问已批准内容。

`resume` 可恢复已落盘、签名仍匹配的待提交批准；没有本地记录但当前会话可核实用户明确批准时，director 用原结论重新调用 signoff。只有“文件生成了”、旧 step 或代理自述，不能推断用户同意。签批后输入变化时保留原批准事实、报告待重审，不把旧批准套到新文件。

## 4. 约束、兼容性与非目标

- 兼容 flow 4 历史，不把历史 step 向前推进当成完整产物证明；旧工程缺回执可检查文件并标“历史产物未登记”，不伪造原始执行记录。
- 新操作记录不改客户源文件和手改字幕；缓存记录不能授予审片批准。
- 不保证跨机器相同绝对路径可直接复用；不恢复第三方 API 额度、不自动发布、不在后台无限重试。
- 同一片子的写入命令加互斥记录；已有活动写入时明确报忙，不能并发修改状态。只读 resume 不阻断；失活锁只在能确认进程已退出时回收，未知主机锁需人工处理。

## 5. 错误处理与运维

失败记录带画幅、阶段、可重跑原命令和已完成产物。强杀遗留 running 读为 interrupted，不能显示“仍在工作”或“完成”。JSON 写入原子替换，保留可诊断错误；损坏记录不算通过。回执中不保存密钥或完整环境变量。只删除本次操作可证明拥有的临时文件。

## 6. 验收标准与测试

- 捕获日志验证：副版准备中的主版比对、声音、渲染、拼接、编码、草稿导出都带准确画幅/阶段，不以副版渲染描述主版检查。
- 相同输入重跑完整产物时，不重复编码或创建草稿；删一个输出只补对应阶段；输入/导出器改变使相关阶段失效。
- 真正创建测试草稿后，在 CLI 登记前模拟中断，恢复返回原草稿而非 `_v2`；用户修改、丢素材、无完成标记、目录同名但非本次拥有分别处理，不覆盖客户数据。
- 纯草稿导出用调用计数与实际可读草稿证明不执行 concat/字幕烧录/MP4 编码；逐镜帧数、字幕和来源仍检查。
- 在签批准备、快照完成、history 提交、Git 提交各边界注入失败，同一批准重试不重复 history，不丢原定稿，不批准发生变化的产物；未批准节点不自动推进。
- 已有 Browser/Remotion 渲染、主副版保护、剪映运行检查与同名避让回归保持通过。
