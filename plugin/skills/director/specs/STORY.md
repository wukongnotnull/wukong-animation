# 剧本填写规范（story.md）

> 剧本是一支片的文字底稿，写给人看，不含代码。以可连贯阅读的故事正文或内容梗概为主体，说明讲什么、为什么值得看、如何推进、最终留下什么；完整人声和屏幕文字单列，供录音与分镜承接。

- **工序**：第 3 道 · 审片节点 ② 剧本
- **模板**：`engine/templates/film/story.md`，第 2 道 `wka init` 建工程时带出空白稿 `films/<片名>/story.md`
- **输入**：签批过的 `brief.md`（核心信息、受众、基调、目标片长、画幅、有无人声、有无配乐）；选定风格的 `STYLE.md`；用户带来的原稿按素材导入流程保存在 `资料/`，例如 `资料/口播稿.md`（用法见「五、有口播稿时」）
- **流程**：怎么提交、征询哪几点见 `../SKILL.md` 第 3 道

## 一、文档职责

正文负责讲清内容，段落表负责检查节奏，人声文案是完整台词的唯一清单。不要在梗概、正文、段落表之间重复讲三遍同一件事；正文描述人物说话的意图或信息变化，不重复粘贴整段台词。

| 容易混淆的 | 区别 |
|---|---|
| 分镜稿 `storyboard.md` | 剧本按**段落**写，分镜稿按**镜头**写。正文可以写具体发生的事、可见的对象和变化；画面怎么拍、景别、运镜、转场、声音铺排、屏幕文字的出现形式都留给分镜稿 |
| 镜头代码 `shots/sNN.js`、片内公共脚本 `shots/common.js` | 画面的代码，第 6 道写 |
| 配乐脚本 `audio/build.mjs` | 合成音乐的代码，第 6 道写 |

模板只保留填写骨架与自检问题；以下类型提示和示例用于辅助写作，不整段复制进交审稿，也不要求逐项作答。

## 二、逐部分写法

| 部分 | 写什么 | 写到什么程度 |
|---|---|---|
| 基本信息 | 标题写片名；链接简报；表里写目标片长、画幅、风格 id | 沿用已签批的简报，目标片长不是录音实长；需要改变已批信息时列入待确认事项 |
| 一句话核心表达 | 一句话说清主要人物与变化、要解释的问题，或要成立的观点 | 让读者能复述这支片的核心；不写“展现了”“体现了”这类空话，不机械限制字数 |
| 创作意图与基调 | 目标受众、预期感受或收获、情绪基调 | 从已批简报提炼简短摘要，不重新征询已确定的需求；基调用 2–3 个具体的词，不违背 `STYLE.md` |
| 故事正文 | 用连贯文字写出全片从开头到结尾的内容，按 `P01 段落名` 等三级标题分段 | 长短随内容需要，读完能复述推进过程和结尾；写具体事件、解释或论据，不只写“引出主题”等功能标签，也不逐镜描述 |
| 段落结构 | 每段一行，写编号、预计时间、推进作用、情绪变化 | 与正文段落顺序一致；作用说明这一段如何推动故事或理解，不复述正文；估时规则见第四节 |
| 人声文案 | 可直接录音的完整原文，每条以 `[P01]` 等段落编号开头，再写说话人和原文 | 旁白写“旁白”，对白写角色名；多角色逐条区分，必要时注明对白、OS 来源或同期原声。标记不读入录音；无人声写“无” |
| 屏幕文字 | 画面上要出现的字：片名、题诗、落款、要点、片尾标识等 | 每条写完整原文及段落编号，引用的诗句注明出处；同一文字跨段使用时列全编号。没有写“无”；不写出现形式。**不包含字幕**：不把人声原文逐句搬进表中，不制作字幕 |
| 自检与待确认 | 回答模板中的五项自检，并集中列出未解决的问题 | 无需数字评分，未满足的项目不勾选；问题写清影响和需要确认的决定，没有待确认事项时写“无”。自检不代替用户签批 |

## 三、正文与类型提示

所有类型都要说清核心表达、观众为何关心、内容如何推进以及结尾留下什么。先写成可连贯阅读的正文，再检查是否缺少支撑；不把这些问题变成额外的必填表单。

| 类型 | 写作提示 | 推进示例 |
|---|---|---|
| 剧情故事 | 主体想要什么，遇到什么阻碍，做了什么选择，选择带来什么变化？ | 想渡河 → 尝试失败 → 改变办法 → 渡河后的发现；起承转合可作参考，不要求四段 |
| 科普讲解 | 观众最初困惑什么，通过哪些现象、例子或解释逐步理解，最后能解释什么？ | 为什么影子会变长 → 比较光照角度 → 用关系解释现象 → 回答最初问题 |
| 观点表达 | 主张是什么，论据如何支撑，哪里需要回应疑问或限定适用范围，观众最后得到什么判断？ | 提出主张 → 给出案例和依据 → 说明边界 → 回到结论；不捏造案例、数据或引用 |
| 意象表达 | 意象如何展开、形成联系和情绪变化，结尾如何回应开头？ | 晨雾中的树 → 光线显出枝叶 → 风过后的静止；不强加人物冲突 |

“情绪变化”既可以是人物或观众的情绪，也可以是理解状态，如“疑惑 → 明白”。确实保持同一基调时写“保持平静”，不为填表制造转折。

## 四、段落编号与预计时间

### 段落对应

- 初稿按阅读顺序使用 `P01`、`P02`……，段落名描述本段内容，段落数量按需要增减，不预设四段。
- 正文标题写 `### P01 段落名`；段落表、人声文案、屏幕文字和分镜稿都引用同一编号。编号仅供文档对应，不是镜号或录音 cue。
- 调整顺序或改段落名时保留编号；新增段落使用未占用编号，删除、拆分或合并时同步检查所有引用，不能留下悬空引用。表格顺序跟随正文，编号不必重新连续排列。
- 无人声或无屏幕文字时，相应部分写“无”并删除占位条目；不把未提供录音误写成无人声。
- 人声只在实际出声的段落列条目，无需每段都有台词。单人旁白也标明“旁白”；角色类型不清时补充“对白（角色）”“OS（来源）”或“同期（来源）”，便于分镜沿用。

人声格式示例（按影片需要选用，不是默认台词）：

```text
1. [P01] 旁白：雨停后，河水仍在上涨。
2. [P02] 小舟（对白）：我们再找一条路。
3. [P02] 阿禾（对白）：先去上游看看。
```

### 估时与实长

- 基本信息保留简报的**目标片长**；段落表填写**预计时间**，例如 `0–6s`、`6–14s`。预计区间首尾相接、不重叠，其总长是本稿的预计总长，不冒充实测结果。
- 检查预计总长是否符合简报中的目标或允许范围；不符时列入待确认事项，说明差额及原因，不擅自修改目标片长或删稿凑数。
- 无录音时，中文每秒约 3.6 字只能作为粗估参考，还需考虑停顿、语气和无台词段落。它用于发现可能超时的问题，不是字数上限；语速与停顿应贴合内容及所选风格。
- 第 4 道以完整录音实长核对。录音与稿件冲突时由用户选择重录或修改剧本并重新确认，不自动改稿；超过已批片长限制由用户决定。
- 第 5 道有人声时按已批准的完整录音和句段定位规划镜头，不为匹配预计时间裁切或变速录音；无人声时沿用已确认的剧本节奏。分镜保留段落编号，解释预计节奏与实际安排之间的差异。

## 五、有口播稿时

用户带来的现成口播稿是创作素材。通过 `wka materials` 导入后，以素材清单登记的实际路径为准，例如 `资料/口播稿.md`；原稿独立保留，始终不改。人声用用户的原句，其余各部分围绕它写。

| 部分 | 怎么用口播稿 |
|---|---|
| 人声文案 | **原句照搬**，按段落加 `[P01]` 等编号与说话人；不润色、不改口吻，口头禅也留着。要改的句子只进改稿建议表，用户同意了才改 |
| 故事正文、段落结构 | 按观点和理解过程分段，正文说明各段展开的内容，段落表只写推进作用、预计时间及情绪变化；估时超出已批目标时列入待确认，不把“片长以稿子为准”当成自动改规格的授权 |
| 一句话核心表达、创作意图与基调 | 从原稿和已批简报提炼，不加稿子里没有的观点；两者不一致时列明差异并请用户决定 |
| 屏幕文字 | 写口播没说出口的那一层：标题写提炼的结论，要点写有素材支持的补充信息，步骤写界面上的原始标签；不逐句照抄口播，不凭空补充事实，也不写出现形式 |

**改稿建议**：无法说清一句话的具体含义或缺少支撑素材时，提出有依据的建议。建议只改人声和内容推进，不写景别、运镜和声音安排。常见的几类：

| 问题 | 表现 | 改法 |
|---|---|---|
| 抽象形容 | 「强大」「丝滑」「直击痛点」 | 换成一个看得见的结果：「改了哪几行，一眼看到红绿」 |
| 一句多点 | 一句里讲了三个功能 | 拆成三句；必要时拆段，或改成步骤 |
| 否定句 | 「你肯定没有」「不用再……」 | 正文给出可以呈现的正面事例，是否改动原句仍由用户决定 |
| 数字无参照 | 「快了 30%」「节省很多」 | 补充有来源的前后对比；无依据时标为待确认 |
| 指代不清 | 「这个」「那边」「它」 | 第一次出现说全名：「Git 图谱面板」 |
| 看不见的动作 | 「我试了很多方法」 | 换成具体发生的事，或有助理解的比喻 |
| 缺素材 | 提到别人的界面、网页、数据 | 句子保留，列出需要的截图、录屏或来源；拿不到时提出改写建议 |
| 句子太长 | 一句 30 字以上一口气说完 | 建议在意思停顿处断句，方便录音 |
| 顺序跳跃 | 讲完 B 又回到 A | 按事件、解释或论证的推进关系提出重排建议 |

连接句（「这只是开胃菜」）、开场和片尾只有一句大字的段落都是允许的，不要求句句有独立画面。

建议写进片目录的 `review/改稿建议.md`，随剧本一起提交：

```text
| # | 原句 | 问题 | 建议改法 | 改后这段讲什么 |
|---|---|---|---|---|
| 1 | 「它的功能特别强大」 | 抽象形容，没有可讲的对象 | 「它能把 20 个分支的合并关系画成一张图」 | 20 个分支的合并关系被画成一张图 |
```

示例中的数量须有素材支持，不能直接当作影片事实。表后附需要用户提供的素材清单（每项写用途）与预计时长，在剧本「待确认事项」链接该建议文件。只将用户同意的改动写入人声文案；用户坚持保留的句子按原句保留。

## 六、签批前自查

导演先核对文档，再提交：

- [ ] 模板各部分已填写；无内容的可选部分明确写“无”，没有遗留“段落名”“说话人”等占位。
- [ ] 正文能连贯阅读，类型提示已用于补足内容，没有变成额外的必填问卷。
- [ ] 正文编号唯一，段落表顺序一致，人声与屏幕文字的段落引用有效。
- [ ] 预计区间连续，预计总长已与目标片长对照；差异明确列出，未以估时代替实际录音。
- [ ] 人声完整且说话人明确；有原稿时逐句一致，每一处改动都有用户同意的依据。
- [ ] 屏幕文字原文与出处齐全，没有把台词当字幕，也没有写出现形式。
- [ ] 正文及段落表没有混入景别、运镜、转场和声音铺排，内容与基调符合 `STYLE.md`。
- [ ] 模板中的五项质量自检按实际情况勾选；未满足项写明问题。影响核心表达、台词或已批规格的事项在签批前解决。

自检完成不代表用户通过。按第 3 道交付与签批流程请用户确认当前剧本；本规范只约束新建或本次明确修订的稿件，不自动改写已有影片或其签批记录。
