# 签批即进入下一工序

Status: Confirmed
Date: 2026-11-10
Source: grilling

## 问题与目标

签批现在既记录交付物是否通过，又把片目录里所有未忽略改动一并提交。提交失败时进度仍可能先被写成通过。工作台显示的是文件副本，用户无法确认页面上的版本就是 Git 中的版本。

本规格把签批改成进入下一工序的唯一决定。用户审阅和放行的是同一次提交；通过后直接进入下一道有效工序。本插件不调用视频生成模型，没有费用开销，不再询问模型、数量、时长、费用或预算。

## 架构与组件边界

影片仓库负责保存待审提交。工作台读取并核对这次提交，接受通过或返修决定，但不启动渲染、不直接改片。制作会话负责在决定生效后执行下一工序。

插件仓库与影片仓库保持分离。影片签批不得暂存或提交插件代码、其他影片或其他无关工作区。

## 接口、数据与行为

- 每次签批前，只暂存当前影片中本次交付物、重新生成这些交付物所需的源文件、校验清单和必要审阅记录。源文件包括 `film.json`、镜头代码和声音脚本。范围外只要存在未提交改动，就拒绝签批。
- 待审内容已与当前提交一致时直接使用该提交，不创建空提交。新提交成功后，工作台立即捕获并切换到这次提交。
- 小样、成片、检查结果及其他 `review/` 媒体继续留在 Git 外。每个待审文件的路径、大小和内容校验值写入这次待审提交。文件内容、大小或校验值变化都会使该提交失去通过资格。
- 工作台在当前交付物旁显示 Git 短提交标识。只有页面打开的文件与该提交中的清单一致时，才显示已提交并允许通过。
- “通过并进入下一步”取代“通过本阶段”。通过前仍须完成本阶段检查、处理阻塞意见并填写结论。通过同时接受该提交，并把制作进度推进到下一道有效工序。方案已排除的副版或剪映草稿直接跳过，不再询问。
- 最后一道有效工序的问题改为“完成制作吗？”。对话中的普通问题改为“进入下一工序：<工序名>吗？”，选项为“进入”和“要返修”。
- 选择返修或“需要修改”必须留下具体修改意见。该决定关闭当前提交的通过资格；修改后必须形成新的待审提交，才能再次签批。
- 对话卡片与工作台共享同一次提交的一个结论。卡片打开期间不做后台监控；卡片返回或收到下一条消息时先读取工作台。先保存成功的结论生效，较晚的相反选择被忽略并告知用户。
- 工作台先通过时，正在等待的制作会话直接开始下一工序。用户稍后回到对话时，说“继续”即按已保存结论开工，不重新签批。
- 审阅结论可以在待审提交之后另记一条。工作台继续把待审提交当作该版本，不把结论提交伪装成交付物提交。
- 新规则从下一次签批开始。已经通过的工序、包括《AGI科普讲解》已通过的方案简报，保留原结论。

## 约束、兼容性与非目标

不恢复任何费用确认，不让工作台启动制作，不重审历史已通过工序，不把无关改动自动塞入提交。旧影片继续只读。现有忽略规则保持媒体文件不入库，但新增的校验清单必须可提交。

提交失败、校验不一致、存在范围外改动、检查未完成或阻塞意见未处理时，不写通过结论、不推进 `.wka/state.json`。

## 错误处理与运维

Git 身份缺失、仓库不可用、暂存范围不明确、文件在提交期间变化或工作台无法打开该提交时，签批停止在待审之前。已有待审提交失去一致性时保留提交历史，但页面明确显示不可通过，并要求重新提交。

结论写入使用现有制作锁串行化。一边已经写好的结论不被后到的另一边覆盖。失败保留待审提交和用户意见，不创建补偿性的空提交。

## 验收标准与测试

1. 未提交交付物、范围外改动、校验不一致或空提交都不能通过；合法待审提交后，工作台显示对应短标识。
2. 小样、成片和检查结果不进入 Git，但其路径、大小和校验值进入待审提交；改动任一字节后旧提交不可通过。
3. 通过把进度推进到下一道有效工序，并跳过已排除工序；最后一道显示完成制作。失败路径不改变进度。
4. 未检查项、阻塞意见或空白返修意见会阻止相应决定；明确返修会关闭当前提交，只有新提交可再次签批。
5. 对话与工作台先后给出相反结论时只保留先保存的结论；稍后返回的会话按该结论继续，不重复签批。
6. 历史已通过工序保持不变。新增测试、工作台回归、lint 和 Git 状态检查覆盖上述行为。
